# Policy Assurance: study-level coding

This folder contains the study-level Policy Assurance coding behind *Proactive, Robust Security at Scale: A Systematization of Intent-Driven Security Policy Automation*. Category definitions and decision rules are in the [codebook](../../Codebook/README.md).

| File | Content |
|---|---|
| `README.md` | Coverage, column definitions, notation, and the coding table |
| `policy_assurance.csv` | The same table in machine-readable form |

## Coverage

Assurance applies only after a policy is operational, and only to an evaluation of whether a deployed intent is being met. The table lists the 39 studies that report such a function: 29 from the general intent-based networking stratum and 10 from the security-oriented stratum. Rows are sorted by paper title.

The 33 studies below were screened for this stage and are omitted because they report no assurance function:

| Reason | Studies |
|---|---|
| The system detects attacks or anomalies, IDS-style, and responds with a new defense policy; it does not track a deployed intent | `basile2026formal`, `castanares2024intent`, `haqdad2026intentbased`, `liu2024intent`, `murcia2025bastion`, `saiyed2026intelligent`, `samdaliri2025pace`, `settanni2024dynamic`, `sun2026neurosymbolic`, `thamizhiniyan2026unifying` |
| The intent goal is embedded in a reward or optimization objective, and no separate conformance finding is produced | `ali2026intentbased`, `asif2025ribn`, `filinis2024intent`, `guo2025ian`, `han2026multillm`, `hussein2025privacy`, `nahum2026intentbased`, `wang2026graphssc`, `wang2026network`, `yu2026agentic` |
| Runtime evaluation is not tied to a deployed intent (generic fault recovery, incident troubleshooting, xApp conflict handling, key renewal) | `ahmad2025scalable`, `salmi2026ainative`, `vilalta2023applying`, `wang2025confucius` |
| Checks are performed only before activation, or on the intended policy set rather than the deployed state | `chowdhary2022intent`, `li2026future`, `rallabandi2025intentdriven` |
| Metrics or feedback are presented to the operator or user, who alone judges conformance | `angi2025llnet`, `leivadeas2021vnf` |
| The post-deployment check is an evaluation performed by the authors, not a system component | `abouelseoud2025practical`, `provvedi2026intentllm` |
| Intents are inferred from deployed configuration without comparison to a target | `mercian2021mind`, `ribeiro2022deterministic` |

## Columns

| Column | Content |
|---|---|
| BibTeX Key | Key of the study in the paper's bibliography |
| Paper | Title, authors, venue, and year |
| Sub-Corpus | `General` or `Security` (the security-oriented stratum, marked `§` in the paper) |
| Assurance Scope | One dominant scope per study |
| Assurance Mechanism | Every mechanism the study reports, separated by semicolons |
| Resolution Routing | Every route the study reports, separated by semicolons |
| Rationale and Evidence | The basis for each decision, with verbatim quotations from the source. Lines are labelled `Scope`, `Mechanism`, `Routing`, and `Evidence`, with optional `Secondary` (a serious alternative that was not counted) and `Note` lines |

## Notation

| Value | Column | Meaning |
|---|---|---|
| Not specified | Assurance Scope | An assurance function is present, but the source does not state what it evaluates |
| Not reported | Assurance Mechanism | An assurance function is present, but no identifiable mechanism is reported (`‡` in the paper) |
| Open loop | Resolution Routing | Deviations are evaluated but not routed |
| (not specified) | Resolution Routing | The source does not state what happens after a deviation is found |
